# The monitoring stack — standby copy

**This copy is not deployed.** The canonical one lives in the Sightline
repository at `helm/monitoring`, and an ArgoCD Application there deploys it
into the `monitoring` namespace.

This exists so the platform can be stood up from here if that repository is
unavailable. Keep it byte-identical to the canonical copy apart from this file:
`infra/monitoringChart.test.ts` over there compares the two `Chart.yaml` files
when this repository is checked out, because a standby that has drifted is a
standby that has never been run.

```bash
diff -r ~/home-assignment/helm/monitoring helm/monitoring   # README only
```

## Only one may run

Both charts deploy a Prometheus. Two of them means each holds half the data,
and together they want about 2.4 GB on a node with roughly one spare — so it is
checked rather than remembered: `MonitoringStackDuplicated` fires on
`count(up{job="prometheus"}) > 1`.

To activate this copy: delete the `monitoring` Application that points at the
Sightline repository, wait for the pods to go, then create one pointing here.
Never both.

## What is _not_ here

Dashboards. Each application ships its own, from its own namespace, which is
what `grafana.sidecar.dashboards.searchNamespace: ALL` in `values.yaml` is for.
This chart is the platform and nothing else — that is precisely what lets
either copy be the active one without carrying the other project's panels.

- this project's dashboard stays in `helm/resume-builder/dashboards/`
- Sightline's are generated by its own kustomize base

Alert rules are the exception and have to live in `values.yaml`: the plain
`prometheus` chart has no rule-discovery sidecar, so rules come from
`serverFiles` or not at all. Both projects' groups are therefore in the active
chart, with this project's unlabelled so the default Slack route keeps them.
